# 餐饮人才 AI 双向匹配工作台设计

## 1. 文档定位

本文定义“餐饮人才”模块第一阶段的 UI 与交互原型。目标是在现有机会星图基础上新增独立的 `/talent` 页面，把招聘与求职整合为同一套可搜索、可解释、可降级的双向匹配体验。

本阶段只验证界面、信息结构、交互与跨浏览器可靠性。所有招聘、求职、匹配度、认证状态和联系方式均为确定性的原型数据，页面必须持续显示“界面原型数据，不代表真实招聘或求职信息”。

## 2. 目标与非目标

### 2.1 目标

- 点击全局“人才”导航后进入 `/talent`，不再进入视觉不一致的旧 GitJobs 首页。
- 用户可在“招聘机会”和“求职人才”之间切换，公共筛选条件保持同步。
- 自然语言输入可转换为可见、可移除、可撤销的结构化条件。
- 招聘卡和求职卡提供餐饮行业需要的高密度事实字段。
- 每条结果显示原型匹配度、推荐原因和风险提示，且能解释评分依据。
- 点击结果在当前页面打开详情抽屉，不发生跨站感或整页跳转。
- 未登录状态可以浏览，但联系方式只显示脱敏占位状态。
- 桌面、手机、键盘、屏幕阅读器和减少动画偏好均具有完整体验。

### 2.2 非目标

本阶段不实现：

- 真实大模型 API 或语义检索服务；
- n8n、Tavily、Firecrawl 或其他采集 Agent；
- 真实招聘发布、求职简历、数据库迁移或后台审核；
- 登录、收藏、联系申请、消息、认领、认证或联系方式解锁；
- 会员、支付、订阅或权益判断；
- 对旧 GitJobs 招聘业务进行迁移或删除。

旧 `/` 招聘底座继续保留，但新的全局人才入口只指向 `/talent`。

## 3. 核心体验

### 3.1 页面框架

`/talent` 复用机会模块的探索轨道、瓷白/深墨蓝主题、紫色 AI 交互色、焦点样式和移动端五项导航。页面由以下区域组成：

1. 全局探索轨道：机会、人才、情报、企业；“人才”标记为当前页面。
2. AI 人才指令栏：接受招聘或求职自然语言描述。
3. 双向模式切换：招聘机会、求职人才。
4. 条件与结果摘要：展示结构化标签、结果数量和撤销入口。
5. 匹配工作台：高密度结果卡片及轻量匹配关系提示。
6. 详情抽屉：在当前页面展示完整事实、匹配解释、风险和联系方式状态。

### 3.2 AI 指令

原型解析器支持确定性关键词，不调用远程 AI。示例：

- “北京找切配，工资 7000 以上，包吃住”
- “招聘川湘菜炒锅，月休 4 天”
- “人在丰台，想找长期后厨工作”

第一版结构化条件包括：

- 模式：招聘或求职；
- 地区：省、市、区；
- 岗位：炒锅、切配、打荷、洗碗、面点、烧烤、服务员、店长等；
- 薪资下限；
- 菜系或技能；
- 经验年限；
- 食宿；
- 月休；
- 到岗时间或用工紧急度。

输入转换出的条件必须可见、可单独删除，并支持撤销上一轮条件修改。模式切换保留地区、岗位、薪资等公共条件，清除只属于另一模式的条件。

### 3.3 招聘卡

招聘卡至少展示：

- 岗位名称、餐饮门店或用工场景；
- 地区；
- 薪资范围；
- 菜系或技能要求；
- 经验要求；
- 工作时长；
- 月休；
- 包吃、包住或房补；
- 发布时间与紧急程度；
- 原型可信度；
- 原型匹配度及两条以内推荐原因；
- 风险提示和联系方式脱敏状态。

### 3.4 求职卡

求职卡至少展示：

- 目标岗位；
- 当前地区与期望地区；
- 期望薪资；
- 从业年限；
- 菜系、工种和技能；
- 可到岗时间；
- 对工时、月休和住宿的偏好；
- 原型认证状态；
- 原型匹配度及两条以内推荐原因；
- 风险提示和联系方式脱敏状态。

页面不得展示真实姓名、真实电话、真实微信或可识别个人身份的照片。

### 3.5 详情抽屉

点击卡片后，桌面端从右侧打开抽屉，移动端使用接近全屏的底部面板。抽屉包含：

- 完整事实字段；
- 匹配条件命中和未命中列表；
- 风险与缺失字段；
- 原型来源说明；
- 更新时间；
- 脱敏联系方式占位；
- “登录后申请联系”禁用态说明。

关闭抽屉后，焦点返回原卡片；Escape 可关闭；抽屉打开时背景不可滚动。

## 4. 原型数据与匹配模型

### 4.1 数据边界

服务端提供两组确定性原型记录：

- 招聘记录至少 8 条，覆盖不同地区、岗位、薪资、食宿和紧急度；
- 求职记录至少 8 条，覆盖不同技能、经验、期望地区和到岗时间。

原型记录不能复用用户聊天中出现的真实电话号码或个人身份信息，也不能暗示真实企业或真实求职者已入驻。

### 4.2 匹配度

匹配度是本地可解释的原型算法，不标记为真实 AI 结论：

- 岗位匹配：30 分；
- 地区匹配：20 分；
- 薪资匹配：20 分；
- 技能或菜系匹配：15 分；
- 经验匹配：10 分；
- 食宿、月休或到岗偏好：5 分。

无条件时不显示虚假的高匹配结论，只展示“等待输入条件”。存在条件时，分数、推荐原因和结果排序必须来自同一组规则。风险提示不参与加分。

## 5. 组件边界

- `TalentPage`：页面壳、模式状态和共享结果状态。
- `TalentCommandBar`：输入解析、条件标签和撤销。
- `TalentModeSwitch`：招聘/求职模式切换及公共条件保留。
- `TalentResultCard`：两种卡片的共同视觉结构和类型特定字段。
- `TalentMatchSummary`：匹配度、推荐原因和风险的文本表达。
- `TalentDetailDrawer`：详情、焦点管理、滚动锁定和关闭行为。
- `TalentFallbackExperience`：减少动画、低性能和手机环境下的完整卡片体验。

组件只消费结构化记录和筛选结果，不自行决定登录、联系方式权限或真实认证状态。

## 6. 数据流

1. 服务端渲染 `/talent` 与安全转义的招聘、求职原型 JSON。
2. 页面初始化探索轨道、主题、模式切换、指令栏、卡片和抽屉。
3. 用户输入自然语言，原型解析器生成结构化条件。
4. 条件变化触发统一筛选与匹配计算。
5. 模式摘要、结果卡、匹配度和详情抽屉使用同一份派生结果。
6. 用户打开详情，抽屉读取所选记录及当前匹配解释。
7. 用户关闭详情，焦点返回触发卡片。

不得把 JSON 直接拼接到可执行脚本中；沿用现有 HTML 标签转义策略，防止 `</script>` 注入。

## 7. 视觉与动效

- 与机会模块共用设计令牌，不创建第二套品牌。
- 招聘与求职通过内容结构、图标和轻微色彩差异区分，不使用性别化颜色。
- 卡片强调薪资、地区、岗位、匹配解释和时效性，避免大面积装饰性留白。
- 动效只用于模式切换、筛选重排、抽屉展开和匹配关系聚焦。
- `prefers-reduced-motion: reduce` 时取消位移和脉冲，只保留即时状态变化。
- 低性能设备不加载额外图形库；核心信息始终可通过卡片读取。

## 8. 响应式与可访问性

- 桌面端：探索轨道 + 主工作台 + 右侧详情抽屉。
- 平板端：收窄探索轨道，详情抽屉覆盖部分内容。
- 手机端：底部导航、单列卡片、全宽模式切换和近全屏详情面板。
- 所有操作可用键盘完成，并具有满足对比度要求的焦点指示器。
- 模式切换使用明确的选中语义；结果数量和无结果状态使用状态区域播报。
- 抽屉使用正确对话框语义、可访问名称、焦点陷阱、Escape 关闭和焦点恢复。
- 卡片信息不能只依赖颜色、图形或动画表达。

## 9. 异常与降级

- 原型 JSON 不可用：展示错误说明和返回机会页入口，不渲染空白工作台。
- 指令无法识别：保留原输入，提示可识别示例，不清除已有条件。
- 无匹配结果：说明冲突条件并允许逐个删除或撤销。
- JavaScript 不可用：服务端仍渲染招聘和求职的基础卡片列表。
- 抽屉目标不存在：关闭抽屉并保留当前筛选，不抛出未处理错误。
- 主题存储不可用：使用系统主题，不阻断页面初始化。

## 10. 验收标准

### 10.1 功能

- `/talent` 可公开访问，人才导航不再指向旧 `/` 页面。
- 招聘和求职模式均有至少 8 条确定性原型数据。
- AI 指令可生成、删除和撤销条件。
- 模式切换正确保留公共条件。
- 卡片、结果数量、匹配度和详情使用同一筛选结果。
- 抽屉可打开、关闭并恢复焦点。
- 联系方式始终脱敏，所有原型边界持续可见。

### 10.2 质量

- Chromium、Firefox、WebKit 覆盖核心桌面、手机、键盘、减少动画和抽屉流程。
- 现有机会页与旧招聘页回归测试继续通过。
- 浏览器控制台无未处理错误。
- Rust 测试、格式、严格 Clippy、模板检查和构建通过。
- 不引入新运行时依赖，不调用生产网络、AI、支付或联系方式服务。

## 11. 实施顺序

1. 路由、页面模板、原型模型和全局人才导航。
2. 人才设计令牌复用、双向模式切换和响应式页面壳。
3. 招聘/求职卡片与确定性筛选。
4. AI 指令、条件标签、撤销和匹配解释。
5. 详情抽屉、联系方式脱敏状态和焦点管理。
6. 三浏览器、移动端、减少动画、控制台与旧页面回归验收。

每一步必须单独验证，并在最终合并前完成独立代码复核。
