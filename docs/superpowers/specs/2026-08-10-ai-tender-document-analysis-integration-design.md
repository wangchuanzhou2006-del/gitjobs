# AI 招标文件分析接入设计

日期：2026-08-10

状态：待用户书面审核

主项目：`foundation-validation`

原型项目：`C:\Users\25351\ai-bid-assistant`

## 1. 背景与决策

`foundation-validation` 是现有主产品，采用 Rust、Axum、Askama 和 PostgreSQL，已经承担统一网站、账户、后台、公开信息采集与人才/机会相关业务。Claude 在 `C:\Users\25351\ai-bid-assistant` 中另行生成了一套 FastAPI、React、PostgreSQL、Redis/Celery、LiteLLM、LangChain 和 Chroma 项目。该原型包含招标文档、企业档案、匹配、风险、标书框架和通知等领域代码，但形成了重复的前端、账户体系和业务数据库。

本设计决定：

- `foundation-validation` 保持唯一用户入口、账户体系、业务后台和最终数据源。
- 不把两个完整产品直接拼接，也不在当前阶段把 Python AI 能力全部重写为 Rust。
- 将 `ai-bid-assistant` 缩减为不面向用户的内部 AI 文档分析服务。
- 第一阶段只交付“上传 PDF、自动分析、查看带原文依据的报告”的可靠闭环。
- 企业匹配、投标价值评分、标书辅助、提醒和 Agent 生态属于后续独立迭代。

长期定位是先做成可独立使用的招标领域 AI 顾问，同时让底层能力具备被 AI Project OS 或其他 Agent 调用的明确接口。当前阶段不建设通用 Agent 平台。

## 2. 第一阶段范围

### 2.1 用户流程

1. 用户在主网站进入招标项目。
2. 用户新建项目，或选择平台已经采集的招标公告。
3. 用户上传一份 PDF 招标文件。
4. 主网站展示任务状态：等待处理、解析中、AI 分析中、部分完成、已完成或失败。
5. 分析完成后，用户在主网站查看统一报告。
6. 用户可以根据失败原因重试；重复操作不得产生无意义的重复任务和模型费用。

### 2.2 报告内容

第一阶段报告包含：

- 项目概况：项目名称、采购单位、预算、服务期限、投标截止时间。
- 资格要求：营业执照、许可证、资质、人员、业绩、注册资本等要求。
- 风险提示：硬性门槛、废标、异常条款、履约和时间风险。
- 材料清单：证照、证明、承诺函和方案文件。
- 原文依据：关键结论对应的 PDF 页码与原文片段。
- 待人工确认：缺失、冲突、低置信度或无法从文件确认的内容。

### 2.3 明确不在第一阶段实现

- 企业条件匹配与匹配分数。
- S/A/B/C 投标价值评级。
- 自动生成完整标书。
- 多 Agent 自动调度。
- 对外开放的生态平台。
- 第二套登录、前端或业务数据库。

## 3. 系统职责与边界

### 3.1 主项目职责

`foundation-validation` 负责：

- 用户、组织、权限和审计。
- 招标项目及其与公开公告的关联。
- 原始 PDF 的接收、校验、存储和访问控制。
- 分析任务的创建、状态展示、重试和取消入口。
- 分析结果的格式验证、持久化和版本管理。
- 报告页面、后台审核和操作记录。
- 后续企业档案、匹配、提醒和投标工作台。

### 3.2 AI 分析服务职责

缩减后的 `ai-bid-assistant` 负责：

- PDF 文本、表格和页码信息提取。
- 扫描版 PDF 的可选 OCR 路径。
- 文本切分、检索和上下文组织。
- 通过统一适配层调用 GPT、Claude 或 DeepSeek。
- 按固定版本的结构返回事实、资格、风险、材料与引用。
- 返回明确的错误类别和可重试信息。
- 处理结束后清理临时文件，不长期保存用户或业务数据。

其现有 React 前端、独立认证和独立用户数据不进入最终产品。可复用的是领域模型思想、提示词、解析/RAG 流程、模型适配与分析服务实现；是否直接保留具体代码由逐模块审查决定。

### 3.3 模块边界

分析能力拆分为独立单元：

- 文档解析：输入文件，输出带页码的文本和表格片段。
- 基本信息提取：只输出文档中明确存在的项目事实。
- 资格提取：区分硬性资格、评分条件、证明材料和普通说明。
- 风险分析：基于已经提取的事实生成风险和建议。
- 材料清单：从资格和正文要求中汇总提交材料。
- 结果复核：检查引用、冲突、缺失字段和可能的模型臆测。
- 模型适配：屏蔽不同模型供应商的调用差异。
- 任务执行：负责异步执行、超时、重试和进度事件。

任一单元可以在不改变主项目业务接口的情况下替换或升级。

## 4. 数据流与通信

### 4.1 正常流程

1. 主项目校验 PDF 类型、大小、页数、加密状态和用户权限。
2. 主项目保存原文件，并创建带唯一幂等键的分析任务。
3. 任务执行器通过内部认证接口将文件或短期授权下载地址交给 AI 服务。
4. AI 服务依次完成解析、检索、提取、风险分析和结果复核。
5. AI 服务返回符合版本化数据契约的结构化结果。
6. 主项目在信任结果前执行数据格式、字段范围和引用完整性校验。
7. 主项目保存报告、引用、模型与提示词版本，并更新任务状态。
8. 用户在主网站查看报告。

本机开发阶段可以通过内部 HTTP 和文件上传通信；部署阶段优先采用私有网络加短期签名文件地址。该差异由文件传输适配层封装，不改变业务流程。

### 4.2 数据归属

主项目永久保存：

- 原始文件及校验值。
- 解析与分析任务、状态和错误。
- 结构化结果、引用和人工修订。
- 使用的模型、提示词版本、数据契约版本和分析时间。

AI 服务只保留完成当前任务所必需的临时数据。默认不持久化用户、组织、企业档案或最终报告。

### 4.3 内部安全

- AI 服务不开放公共用户入口。
- 主项目与 AI 服务使用可轮换的内部身份凭证。
- 每个请求关联主项目生成的任务 ID，不信任 AI 服务传回的用户身份。
- 文件访问采用短期授权，并限制文件类型、大小、页数和处理时长。
- AI 输出只能经过固定数据契约进入数据库，不能直接执行数据库写入或系统操作。
- 日志不得记录完整证照、密钥或整份文件内容。
- 后续处理企业敏感资料时，按模型供应商配置数据外发策略；不满足策略时禁止调用相应外部模型。

## 5. 分析数据契约

第一版数据契约使用版本号，例如 `tender-analysis.v1`。顶层至少包含：

- `project_info`：项目基本事实。
- `qualifications`：资格要求列表。
- `risks`：风险列表。
- `required_materials`：材料列表。
- `unknowns`：缺失、冲突和待复核事项。
- `analysis_meta`：模型、提示词版本、契约版本和完整度。

每条关键结论至少包含：

- 稳定的条目标识。
- 结论类型和规范化值。
- 文件中的原始表述。
- 一个或多个引用：页码、原文片段、文档片段标识。
- 置信度等级。
- 是否需要人工确认。

资格条目还必须标明其性质：硬性资格、评分项、提交材料、合同履约要求或普通说明。风险条目必须把事实依据、风险判断、潜在影响和建议分开存储。

金额保留原始币种和单位；规范化金额只能作为派生字段。日期无法确认时返回未知，不擅自推算。同一字段在不同页面冲突时，不选择性覆盖，而是返回冲突记录。

## 6. 提示词与 RAG 设计

### 6.1 分步提示词

分析采用可测试的分步提示词，而不是单次生成整份报告：

1. 基本信息提取：只识别名称、单位、金额、日期和期限等事实。
2. 资格与材料提取：识别要求并分类其法律或业务性质。
3. 风险分析：只基于前两步事实和检索到的原文判断风险。
4. 结果复核：验证引用覆盖、字段冲突、缺失内容和输出格式。

### 6.2 共同约束

所有提示词必须要求模型：

- 不根据常识补写文件中不存在的信息。
- 不把评分加分项误判为准入资格。
- 不把建议写成文件事实。
- 所有关键事实提供页码和原文；无依据时标记未知。
- 明确报告互相矛盾的原文。
- 输出固定结构，不夹带额外说明文本。
- 将低置信度结果放入人工复核范围。

提示词、数据契约和模型配置分别版本化。升级任一部分时可以重新运行分析，同时保留旧报告用于对比和追溯。

### 6.3 检索原则

文本切分保留页码、章节标题、表格位置和片段顺序。检索针对具体问题选择相关片段，不能只依赖向量相似度；金额、日期、否定词和资格条款需要结合关键词或规则检索。第一阶段不以建设通用知识库为目标，RAG 只服务于当前招标文件的可靠分析。

## 7. 状态、错误与恢复

任务状态为：等待处理、解析中、AI 分析中、部分完成、已完成、失败。

- 模型限流、短时网络错误和临时服务故障：有限次数自动重试并退避。
- PDF 损坏、受密码保护或完全无法解析：停止重试，给出用户可理解的原因。
- 扫描件未启用 OCR 或 OCR 质量过低：标记部分完成或失败，不能伪造完整报告。
- 输出不符合数据契约：拒绝保存为有效报告，可用同一任务触发受控重试。
- 部分字段无法识别：保存其他有效结果，将缺失字段放入 `unknowns`。
- 重复提交：按文件校验值、项目和分析配置生成幂等键，复用有效任务或由用户明确发起新版本分析。

任务必须记录对用户友好的错误信息和供运维排查的内部错误代码，后者不得泄露密钥或敏感文件内容。

## 8. 测试与验收

### 8.1 自动化测试

- 数据契约校验：合法、缺字段、类型错误、越界值和未知版本。
- 文档解析：文本型 PDF、扫描件、表格、空页、损坏和加密文件。
- 引用验证：页码范围、原文片段存在性、无引用关键结论。
- 任务执行：幂等、重试、超时、部分完成和失败恢复。
- 内部接口：认证失败、超大文件、非法类型和重复请求。
- 主项目集成：上传、状态轮询或推送、结果落库和报告展示。

模型相关测试默认使用固定样例或模拟响应，避免普通测试依赖外部模型费用和不稳定输出。另设人工运行的真实模型评估集。

### 8.2 真实文件验收

至少建立三类脱敏样例：

- 文本型招标 PDF。
- 扫描版招标 PDF。
- 包含复杂表格和多个附件的 PDF。

人工重点核对项目金额、截止日期、资格条件、材料、页码引用和未知项。任何无原文支撑的关键事实视为失败。第一阶段完成标准是：用户能够在同一网站上传真实 PDF，看到清晰、可追溯的分析报告，并在失败时获得明确原因和重试入口。

## 9. 后续升级路径

在第一阶段通过真实文件验证后，按独立设计与实施周期逐步增加：

1. 企业档案和硬性资格规则判断。
2. 可解释的企业匹配结果。
3. 结合匹配、地区、金额、竞争和经验的 S/A/B/C 投标价值评分。
4. 材料任务、负责人、进度和截止提醒。
5. 标书目录、技术方案、服务方案、人员配置和应急预案框架。
6. 多文件联合分析和企业知识库。
7. 供 AI Project OS 或其他 Agent 调用的授权接口。

后续评分遵循“确定性规则优先、AI 负责解释和处理非结构化信息”的原则。任何评分都必须展示构成因素、缺失信息和原文依据。

## 10. Codex 与 Claude 协作规则

Codex 负责架构、接口契约、数据结构、提示词、任务拆分、验收标准、代码审查和修正提示词。Claude 负责按单个任务包实现代码、迁移和测试。用户确认产品方向并将任务包交给 Claude。

每个 Claude 任务包必须包含：

- 单一明确目标和非目标。
- 允许修改的目录与文件范围。
- 必须阅读的现有代码和设计文档。
- 不得创建第二套产品、登录、用户数据库或前端的约束。
- 输入输出契约、错误行为和安全要求。
- 必须新增或运行的测试。
- 完成后需要报告的文件清单、设计偏差和测试结果。

固定协作流程：

1. Codex 编写单模块任务包。
2. Claude 实现并报告变更与测试。
3. Codex 检查实际差异和测试证据。
4. 不满足设计时由 Codex 给出精确修正提示词。
5. 当前模块验收后才开始下一模块。

Claude 未经明确批准不得扩大范围、替换主技术栈、顺手重构无关模块或在其他目录创建新项目。

## 11. 第一阶段实施拆分原则

正式实施计划将在本设计审核通过后单独编写。计划应优先形成端到端窄切片，而不是先把任一系统大面积改造。建议顺序为：

1. 固定并测试 `tender-analysis.v1` 数据契约。
2. 审查 Claude 原型中可复用的 PDF 解析和模型适配代码。
3. 建立最小内部分析接口及模拟实现。
4. 在主项目建立分析任务和结果存储。
5. 打通上传、异步处理和状态展示。
6. 接入真实解析、分步提示词和引用验证。
7. 完成报告页面、错误恢复和真实文件验收。

每一步均应有独立测试和回退边界；不得一次性迁移原型中的全部模块。
